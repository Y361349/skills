# 需求评估（E0）

## 目标

- 在进入代码阶段前，确认需求可执行、可验证、可控风险。
- 输出后续路径：`tweak` 或 `analyze`。

## 边界

- 仅分析用户输入与会话上下文。
- 默认禁止在本阶段扫描仓库文件或读取代码实现（保持“纯需求评估”）。
  - 例外：当用户请求为“方案包评分评审/why-how-task 评审”时，默认进入“只读锚点核验”（仅验证锚点是否存在/是否覆盖关键模块，不做实现建议/不写入代码）；若用户明确要求“仅评分不核验”，才跳过锚点核验。
- multi_agent 只读并行（默认自动启用）：除非用户显式禁用（例如：`HA_MULTI_AGENT=off` 或口头“单代理/不要子代理”）
  - 常规需求评估：若已确认 `multi_agent` 可用且 roles 已配置，主代理应默认并行 spawn `ha_product`（产品/验收视角）与 `ha_reviewer`（风险/EHRB 视角）给出独立评分建议与追问列表；主代理汇总后给出最终评分与下一步（spawn 失败则降级为单代理评分）。
- 方案包评分评审（默认含锚点核验）：在上述基础上，若未禁用（`HA_EXPLORER_SLICES=off`），额外并行 spawn explorer 做锚点核验：
    - explorer 数量默认 **2~4**（按 `references/multi_agent.md#3.3` slice 分片；上限=4）；若用户显式指定 `HA_EXPLORER_SLICES=2|4`，按其覆盖。
    - `BACKEND`：优先只检索 `<backend_root>/`（若能识别）；否则用 `**/*.java|**/*.kt|**/*.go|**/*.py|**/*.cs` 等 glob 全仓兜底。
    - `FRONTEND`：优先只检索 `<frontend_root>/`（若能识别）；否则用 `**/*.vue|**/*.ts|**/*.tsx|**/*.js|**/*.jsx` 等 glob 全仓兜底。
    - `DB`：仅当方案包明确涉及 SQL/落库/迁移/表结构时启用；glob 示例：`**/*.sql`。
    - `DOCS_CONFIG`：仅当方案包明确涉及配置/权限点/环境差异/文档约定时启用；glob 示例：`**/*.md|**/*.yml|**/*.yaml|**/*.toml|**/*.json|**/*.env*`。
    - scope/分片确定方式（强制，保证全局通用）：主代理先做“仓库形状探测”（顶层目录 + 构建/依赖清单文件，如 `pom.xml`/`go.mod`/`package.json`），能判定就收敛到目录 scope；探测到多个候选 root 时可按 root 分片增加 explorer 数（建议 ≤4）并行核验；仍不确定则向用户追问。
    输出“已覆盖/缺失/未确认锚点清单 + 关键词”，避免重复扫描。
  - 提效建议（默认启用）：锚点核验优先使用 `ha_explorer_fast`（若未配置则用 `ha_explorer`）；需要深挖 1-2 条关键调用链时再由主代理第 2 轮 spawn `ha_explorer_deep`（若未配置则用 `ha_explorer`）。
- 若用户显式 `UI=on` 或需求包含页面/交互/视觉等关键词：可额外并行 spawn `ha_ui_designer` 输出“UX/UI 待确认问题”，用于提升评分与后续方案可执行性。

## 评分模型（总分10）

1. 目标清晰度（0-2）
2. 问题现状（0-2）
3. 验收标准（0-3）
4. 范围边界（0-2）
5. 约束与风险（0-1）

## 评分机制（v2，可复现，推荐默认）

> 为解决“同一方案包在不同会话出现 9.x vs 8.x 大幅波动”的问题，本阶段默认采用可复现评分卡：`references/scoring.md`（Scorecard v2）。

强制规则（适用于任何项目）：  
- **最终分数必须由主代理按评分卡逐项机械计算**（禁止“感觉分”）。子代理（`ha_product/ha_reviewer/ha_explorer*`）只输出“缺口/风险/锚点核验结果”，不得直接用其总分替代主代理计算。  
- **不得沿用输入里自带的分数**（例如 why.md 中的“综合评分”）；只能作为“历史记录”引用，必须重新计算。  
- 当用户请求“评分/评审/打分”（含方案包 why-how-task 评审）：必须输出 **双分制**：  
  - `S_doc`（方案表达分）：只看文本  
  - `S_ready`（落地就绪分）：含锚点核验 + 阻断项封顶（用于是否进入实现/是否放行）  

硬门槛：
- 验收标准 < 2 分，评分上限 7。
- 范围边界 < 1 分，评分上限 7。
- 出现 EHRB 且未说明关键安全条件，评分上限 6。

## 评分后动作

- 评分 >= 8：进入复杂度判定。
- 评分 < 8：输出追问（3-5个），等待用户补充。
- 用户输入“以现有需求继续”：允许强制继续，并在后续总结标注风险。
- 用户输入“取消”：终止本次流程。

## 复杂度判定

- `TWEAK`：单点小改、实现路径明确、无高风险。
- `LIGHT`：局部变更，需要简要设计。
- `STANDARD`：跨模块/多路径/架构变化/高风险。

判定结果映射：
- `TWEAK` → `tweak/SKILL.md`
- `LIGHT`/`STANDARD` → `analyze/SKILL.md`

## 交付模式判定（DELIVERY_MODE）

目标：让“简单需求”在不走 CSV 台账的情况下也能完成闭环交付（同步知识库（必做） → 记忆体 → 本地 git commit）。

- 默认规则（可被用户指令覆盖）：
  - `TWEAK` / `LIGHT`：`DELIVERY_MODE=CLOSE_LOOP`
  - `STANDARD`：`DELIVERY_MODE=NORMAL`（建议改走 `issues-csv-exec-with-wiki` / `/prompts:issues_csv_execute_with_wiki` 做强闭环台账）
- 用户显式要求跳过某一步（如“不提交/不写记忆体”）时：允许跳过，但必须在最终输出中写清原因与风险。
- 知识库同步为交付必做项：默认不允许跳过；若用户坚持跳过，必须二次确认并在最终输出中标注风险。

## EHRB 风险信号

常见信号：
- 删除/覆盖大量数据
- 权限系统或认证核心改动
- 支付/订单/隐私数据改动
- 生产环境高风险操作

处理规则：
- 标记风险并强制升级到 `STANDARD`。
- 要求后续阶段加入回滚与验证方案。

## 输出要求

- 使用 `templates/output-format.md`。
- 评分不足时只输出追问，不输出实施建议。
- 评分通过时必须展示：`S_ready`（以及在“评分/评审”场景下同时展示 `S_doc`）、复杂度、交付模式、下一阶段。

## 阶段退出条件

- 评分通过并完成复杂度判定。
- 用户取消。
- 用户要求暂停，等待下次继续。
