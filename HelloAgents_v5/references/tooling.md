# 工具协同（HelloAgents_v5）

> 目的：用“先定位、再精读、再语义确认、最后最小改动”的方式，把上下文和风险控制在最小必要范围内。

## 1. 决策树（优先级）

1) **跨文件定位/枚举** → `code-index`  
2) **精读文件/片段** → Desktop Commander（优先 `read_file` + `offset/length`）  
3) **语义正确操作**（类型/签名/诊断/重命名/格式化）→ `mcp-lsp-bridge`  
4) **修改文件** → Desktop Commander（`edit_block`/`write_file`，外科手术式最小替换，保持 UTF-8）  
5) **运行/构建/测试/脚本** → `exec_command`（PowerShell 注意编码与转义）

> 兜底原则：工具不可用时，退回到“更朴素但可靠”的方式（例如 `code-index` → Desktop Commander 搜索；`mcp-lsp-bridge` → 纯文本搜索 + 小步修改 + 更强验证）。

## 2. `code-index`（定位优先）

**适用：**
- 找“哪些文件可能相关”（按文件名/目录/扩展名）
- 找“某段文本/某个符号在哪里出现”
- 粗略评估影响面（命中分布、引用次数）

**最小流程（每个新会话/新仓库）：**
1. `set_project_path(<项目根目录>)`
2. （可选）`refresh_index`（仅当索引缺失/明显过期/需要追最新变更时）
3. （可选）需要符号级能力时再 `build_deep_index`（成本更高，避免不必要调用）

**子代理协作约束（multi_agent 场景，强制）：**
- 现实约束：`code-index` 常以 stdio 方式在“每个 agent thread”内各自启动 MCP 子进程；进程之间不共享内存上下文。子代理在本线程首次使用 `code-index` 前，需要先执行 `set_project_path(<项目根目录>)` 绑定项目根目录（必要步骤）。
- 为避免重复重建/重复 I/O：子代理默认**不要**调用 `refresh_index/build_deep_index`；若确实需要最新索引或符号级能力，优先由主代理统一执行后再分发命中结果（或主代理明确授权子代理执行，并要求在输出中说明原因）。
- 若你的 `code-index` 实现支持“单 watcher / 共享索引产物”的开关，建议开启（例如本机 `code-index-mcp-session-isolation` 支持 `CODE_INDEX_MCP_SINGLETON_WATCHER=1`）；否则请把重操作收敛到主代理，子代理只做只读查询与精读取证。

**常用策略：**
- 先 `find_files`（小范围）再 `search_code_advanced`（精确文本/正则）
- 命中后不要立刻全文读取：先拿到文件路径与行号，再用 Desktop Commander 片段精读

## 3. Desktop Commander（精读与上下文控制）

**适用：**
- 读取文件内容（片段优先）
- 列目录、确认文件是否存在
- 在 `code-index` 失败或未配置时做全文检索（`start_search`）

**关键约束：**
- 优先用 `offset/length` 分段读取，避免一次性塞满上下文
- 修改文件时：读取必要上下文 → `edit_block` 外科手术式替换 → 再读回关键片段自检

## 4. `mcp-lsp-bridge`（语义正确性优先）

**适用：**
- 不确定类型/签名/重载（`hover` / `signature_help`）
- 需要“真正的引用/实现/调用层级”而不是字符串匹配（`references` / `implementation` / `call_hierarchy`）
- 安全重命名（`rename` 先预览再应用）
- 格式化（`format_document` 先预览再应用）

**使用建议：**
- 先用 `code-index` 定位到文件/范围，再用 LSP 做语义确认，成本更低、命中更准

## 5. Desktop Commander（最小改动）

**原则：**
- 只改“为满足需求/修复问题”所必需的最小集合
- 避免顺手重构、避免无关格式化（除非验证失败或规范要求）
- 保持 UTF-8；避免引入不可见字符/乱码

## 6. `exec_command`（验证与回归）

**适用：**
- `npm test` / `pnpm test` / `pytest` / `mvn test` 等
- 构建、lint、格式化（若项目已有工具）

**multi_agent 场景门禁（强制）：**
- 测试/构建/回归命令必须只能由主代理串行执行；子代理禁止跑测试与回归（避免环境争用、结果不可追溯）

**建议顺序：**
1) 先跑与你改动最相关的最小命令  
2) 再扩大到更全面的测试/构建  

## 7. 常见“负优化”警示

- **过度读取**：为“看起来更懂”而把大量无关文件读进上下文 → 降低准确率、增加幻觉概率  
- **过度依赖某工具**：把流程写死在某个 MCP/命令上，导致环境差异时失败  
- **大改动一次到位**：难定位回归原因；应拆小步、每步可验证  

## 8. 并行与 `multi_agent`（必须说清楚）

> 目的：避免把“并行只读收集”和“子代理并行写入”混为一谈，导致方案包不可执行或触发失败。

### 8.1 两种“并行”能力

1) **工具级并行（推荐，若环境支持）**  
同一轮内可用 `multi_tool_use.parallel` 并发执行**只读/无副作用**的工具调用，用于加速上下文收集。  
说明：`multi_tool_use.parallel` 属于运行环境提供的并发包装器，是否存在取决于客户端/运行时能力，不取决于“是否新对话”；若不可用则降级为串行调用即可。  
典型：并行 `code-index` 检索 + 并行精读多个文件片段（Desktop Commander `read_file offset/length`）。

2) **`multi_agent` 子代理（可选，受控使用）**  
Codex 的多代理能力，需要显式启用（例如：`[features].multi_agent = true`，或在 CLI 用 `/experimental` 启用 Multi-agents 并重启）。  
HelloAgents_v5 在满足门禁且 roles 已配置时，会在 `evaluate/analyze/design` 阶段**默认自动** spawn 只读子代理（如 `ha_explorer/ha_reviewer/ha_product/ha_ui_designer`）做评分/并行收集与决策补齐；若 spawn 不可用/失败则自动降级为单代理串行，不影响交付。

### 8.2 本技能的并行策略（强制口径）

- **只读并行（允许）**：检索定位 + 并行精读片段，用于加速“找真相源/补证据/消歧义”。  
- **写入默认串行（必须）**：决策定稿、补丁合并、验收、验证与回归（测试/构建）必须由主代理串行执行。  
- **受控并行写入（允许但门槛高）**：只有在主代理已定稿并产出“写入包”后，才允许借助 `multi_agent` 并行分发写入；否则禁止。

### 8.3 `multi_agent` 使用约定（最小可执行）

- **可用性门禁**：未确认启用 `multi_agent`（`[features].multi_agent = true` 或 `/experimental`）→ 视为不可用，所有写入回退为单代理串行。  
- **code-index 索引门禁**：必须先由主代理完成 `code-index` 初始化与建索引，子代理才允许调用只读查询（见 `#2. code-index`）。  
- **分工边界**：子代理只做两类事：  
  - A) 只读检索/精读 → 回传“证据锚点 + 结论摘要”  
  - B) 按“写入包”落地写入 → 子代理不得补全/推理/改口径/扩范围；冲突则停止回报  
- **写冲突控制**：不同子代理不得写同一文件；同一文件多处修改默认由主代理合并后一次写入。  
- **主代理验收门禁**：子代理写入完成后，必须由主代理验收（查看 diff + 回读关键片段 + 最小相关测试）；验收不通过不得进入下一任务。  
- **测试/回归门禁**：所有测试/构建/回归只能由主代理执行；子代理禁止运行（即使只是“帮忙跑一下”）。  
- **最小验证**：最可靠的检查方式是跑一次最小协作流程并观察是否真的 spawn 了子代理；若无法 spawn/无回传结果，则按不可用处理。
